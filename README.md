# Matterhorn

Matterhorn is a verdict-free causal literacy engine. Given a viral narrative it renders the
causal skeleton the story implies: the asserted spine, every edge labelled by evidence status,
and beside it the branches the story priced at zero, such as the absent denominator, the missing
counterfactual, and who bears the cost first. Every number on screen carries a source identifier
that resolves in `content/sources.json`, or the renderer throws instead of drawing it. The
product never says true or false and never scores an outlet.

## What this build is, precisely

A demo archive of ten narratives, six in an Indonesia pack and four in an EN-Global pack, each
dissected once at editorial time by an agent fleet and published as static JSON under
`content/`. The app fetches those artifacts over HTTP and renders them. That is the entire read
path.

- Nothing is analysed when you open the site. There is no backend, no serverless function, no
  API endpoint, and no model call at runtime.
- The repo holds no API key and no `.env` file, and the shipped app reads no environment
  variable. `pipeline/config.ts` declares a typed `api` executor that is deliberately not wired
  and refuses if it is selected.
- Pasting or sharing a link does not dissect it. Links resolve against `content/url_index.json`
  by exact, prefix or regex match; a miss renders a queue state rather than inventing an
  analysis. Exactly one entry is flagged `fresh_demo` and plays a staged progress animation over
  an artifact that was already computed.
- Every published artifact carries its own manifest: which model ran which pipeline slot, when,
  over what input hash, plus the two gate verdicts and their tokens.

## Requirements

Node 22 or newer, and pnpm (the repo pins `pnpm@10.33.2` via `packageManager`).

```
pnpm install
```

## Run it locally

```
pnpm dev          # vite dev server, http://127.0.0.1:5173
```

The dev server reads the published archive itself. `app/vite.config.ts` points
`__CONTENT_BASE__` at `content/` over vite's `/@fs`, so dev and a production build differ only in
how the bytes are reached. The frozen Gate 2 grammar fixtures under `tests/fixtures/seed` are
reachable only in harness mode (`vite app --mode harness`), which is what keeps them out of the
shipped bundle and out of the app import graph; the validator asserts that separately.

To serve the real build:

```
pnpm build
rm -rf app/dist/content && cp -R content app/dist/content
pnpm preview      # http://127.0.0.1:4173
```

Routes, all client-side except the permalink shells (`app/src/routes.tsx`):

| Route | What it is |
|---|---|
| `/` | scroll-driven landing |
| `/app` | the mobile app shell; inside a phone frame at 768px and up |
| `/n/{id}` | public permalink, mounts the app straight onto that autopsy |
| `/research` | desktop research desk: archive table, constellation, exports |
| `/methodology` | the published methodology, same body the in-app screen draws |
| `/share` | Android Web Share Target, resolves the incoming link |
| `/offline` | what the service worker serves for an uncached navigation |

## Regenerate the content

Content is not generated by `pnpm build`. It is produced by a separate thirteen-stage pipeline
driven one stage at a time:

```
pnpm pipeline stage <A1..A13> --run <run dir> [--narrative <id>] [--out <content root>]
```

`--run` is the only place a stage reads and writes state. `--out` is the content root A12 and
A13 write into, so a dry run never publishes into `content/`. Exit 0 on success, 1 on a refusal
with the reason, 2 on a usage error.

Six stages are deterministic code and run to completion in the runner: A1 scout (reads
`pipeline/snapshot/registry.json`), A2 normalise, A3 cluster, A4 rank, A12 publish, A13
librarian.

The seven LLM slots, A5 to A11, are **not** executed by the runner. Under the shipping
`claude-code` executor the runner writes `<run>/slots/<narrative>/<role>.input.json`, an
orchestrating agent session runs that slot as a Claude Code subagent, and the next invocation of
the same stage validates the staged `<role>.json` against `pipeline/agents/<role>.schema.json`
and ingests it. So regenerating content is an orchestrated session, not one command. Slot
prompts live in `pipeline/agents/prompts/`, the model floor per slot in `pipeline/config.ts`.

Two rules the rest of the build leans on:

- A10 (Symmetry Auditor) and A11 (Fidelity Guard) can block publication. The model returns a
  judgment; the runner mints the token, which is a sha256 over the artifact bytes.
- A12 publishes nothing unless both verdicts read pass and both tokens verify against the exact
  bytes it is about to write, and it reads no clock, so two runs over the same inputs are byte
  identical. A block binds the bytes it judged: a superseded candidate is named in the log, the
  same bytes are refused forever.

After a run, the archive has to pass the validator before it means anything:

```
pnpm validate:content
```

Ten checks from blueprint 6.11, every one run on every invocation: schema, orphan numbers,
recomputed counts, narration binding in both languages, banned-lexicon and future-tense-harm
lint, manifest and gate tokens, seed quarantine (including a scan proving no app module imports
a fixture), url index, source liveness, pack feeds. It never touches the network.

`pnpm build:content-review` regenerates `content-review.md`, the operator's editorial sheet:
every sparring question with its correct answer, every lean assignment, every status.

## Checks

```
pnpm lint            # eslint
pnpm typecheck       # tsc --noEmit
pnpm test:unit       # vitest, the app and validator suites
pnpm test:pipeline   # vitest, pipeline unit tests and evals
pnpm test:e2e        # playwright, the state matrix and flows
pnpm validate:content
```

CI (`.github/workflows/ci.yml`) runs lint, typecheck, `test:unit`, `validate:content` and
`build` on every push. Every step is blocking; there is no `continue-on-error` in the file. The
e2e suite and the pipeline evals are not in CI, which is recorded as a gap in `.crown/notes.md`.

## Deploy

The deployment is static files. `vercel.json` sets `outputDirectory` to `app/dist`, a build
command of `pnpm build && pnpm build:permalinks && pnpm build:seo`, `cleanUrls`, an SPA rewrite
that excludes the real files, immutable caching for `/assets` and `/icons`, revalidate-always
for `/content` and the worker, and a content security policy with `script-src 'self'` and
`object-src 'none'`. No third-party runtime script is loaded anywhere.

Two things to know before deploying:

1. `app/src/site.ts` exports `SITE_URL` as the placeholder `http://localhost`. It is the origin
   stamped into og tags and the sitemap, and it has to be replaced with the deployed origin.
   Nothing else in the repo changes.
2. `pnpm build` emits the app bundle and the `/n/{id}` permalink shells, then asserts the
   performance budgets on what it emitted (`pnpm check:build`, which can fail the build). It does
   not copy content. The served root also needs the archive at `/content`, which the app fetches,
   and the fetched link previews at `/assets/og` (eight of the ten artifacts point at
   `/assets/og/{id}.jpg`; the two fallbacks carry no image path). The Playwright preview configs
   under `tests/e2e/` copy those trees in explicitly before serving; a deployment has to do the
   same.
